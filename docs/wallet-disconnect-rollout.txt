Protocol:
- Shared funds live at bot; merging site funds uses a durable debit receipt and a reference-deduplicated bot credit.
- Site serializes the account with its existing wallet mutex. A durable pending option blocks new site wallet mutations.
- Bot prepare locks user balance; persists transfer ID and destination; removes the exact account link atomically. For site destination, the entire current balance is debited to transfer escrow. For bot destination it remains at bot.
- Bot wallet API rejects stale site requests under the same user row lock after unlink. Bot's own wallet purchases already lock that row.
- Site credits a single approved ledger receipt only for site destination, clears local link and records local_applied in one transaction.
- Commit acknowledges local application; repeat calls return the original amount. Site releases its durable freeze only after acknowledgment.
- Transfer IDs are generated by server, bound to user/phone/site ID/destination. Destination cannot change after prepare.
- An ambiguous result is retried with the SAME ID. Never manually credit/refund the same transfer merely because an HTTP call timed out.
- Pending user receipts prevent starting disconnect. Operator investigation may be needed for unresolved older transactions.
- Re-link is blocked while a bot transfer is prepared. Old admin unlink is disabled to prevent bypassing destination selection.

Recovery / rollback:
- Do not restore an old wallet implementation or drop transfer tables while any transfer is prepared/local_applied.
- Resume from customer account page with recorded destination. Inspect both journals if unavailable.

- A bot-only prepared transfer to site has funds escrowed, not lost. Do not recredit bot unless an audited compensating protocol proves site never credited it.
- Never log credentials, account-link codes or full Telegram update bodies.
