# تخفیف پلکانی کاربران عادی — راهنمای بازبینی و انتشار

این تغییر در `/private/tmp/bot-customer-loyalty` و کپی مستقل افزونهٔ سایت در `/private/tmp/bot-loyalty-wordpress` پیاده‌سازی و با دیتابیس SQLite حافظه‌ای و HTTP ساختگی آزموده شده است. هیچ تغییر مالی روی سایت/ربات، پیام تلگرام، مهاجرت دیتابیس واقعی، restart یا انتشار اجرا نشده است. یک درخواست بدون کلید و بدون دادهٔ تغییردهنده به API تنظیمات سایت صرفاً برای تشخیص دسترسی انجام شد؛ پاسخ ۴۰۴ بود.


## رفع خطای دکمه‌های مدیریت — ۲۶ سپتامبر ۲۰۲۶

در بررسی بدون احراز هویت، `POST https://ip-sabet.me/wp-json/ipsvp/v1/sync/customer-loyalty/settings` پاسخ `404 rest_no_route` داد. مسیر API روی سایت آنلاین ثبت نشده بود؛ انتشار کد ربات به‌تنهایی آن را ایجاد نمی‌کند. فایل‌های آمادهٔ سمت سایت در مخزن محلی `/Users/mojtaba/Documents/ip-sabet-wordpress` قرار دارند (وصلهٔ معادل نیز در بستهٔ بازبینی است).

برای انتشار توسط مالک، هر دو مخزن باید منتقل شوند:

1. **سایت:** پنج فایل درج‌شده در `wordpress.patch` را همراه یکدیگر منتشر کنید؛ فایل ورودی افزونه باید `includes/class-ipsvp-customer-loyalty-sync.php` را بارگذاری کند. صرفاً کپی‌کردن فایل کلاس کافی نیست. افزونهٔ `ip-sabet-pasarguard-shop` باید فعال باشد. این تغییر افزایش نسخهٔ افزونه یا migration ندارد.
2. **ربات:** کد این اصلاح را منتشر کنید. `WP_BASE_URL` همان نشانی سایت و `WP_SYNC_SECRET` همان کلید مشترک فعلی باشد؛ کلید تازه یا نمونه جایگزین نشود. مقادیر اکنون از `config/services.php` خوانده می‌شوند تا با کش لاراول سازگار باشند. پس از تنظیم محیط، طبق روش استقرار خودتان `php artisan config:cache` را اجرا کنید. این فرمان اینجا فقط روی کپی آزمایشی اجرا شده است.
3. **اتصال مشترک:** برای حساب‌های متصل، در `wp-config.php` قبل از بارگذاری وردپرس `define('IPSVP_CUSTOMER_LOYALTY_BOT', true);` لازم است. پیش از فعال‌سازی، endpoint رویدادهای ربات باید با کلید مشترک در دسترس سایت باشد. ثابت موجود را دوباره تعریف نکنید. قیمت‌گذاری ربات نیازمند `CUSTOMER_LOYALTY_ENABLED=true` و فهرست شناسه‌های واقعی سرویس اشتراکی است؛ نمایش سطح به این flag وابسته نیست.
4. **بررسی پس از انتشار:** درخواست بدون کلید به مسیر تنظیمات باید به جای `rest_no_route` پاسخ عدم دسترسی بدهد؛ سپس داخل ربات دکمهٔ پلکان، تخفیف ثابت (صفر و پاک‌کردن) و حساب کاربری را بررسی کنید. با کلید صحیح، خواندن تنظیمات باید `ok:true` بدهد. این بررسی زندهٔ احراز هویت‌شده هنوز انجام نشده است.

پیام‌های ادمین اکنون خطای ۴۰۴، کلید نامعتبر/غایب، اتصال غیرفعال و اختلال شبکه را جدا نشان می‌دهند. کلید، بدنهٔ درخواست و رویدادهای مالی در لاگ تشخیصی نوشته نمی‌شوند. صفحهٔ حساب هنگام قطع سایت همچنان باز می‌شود، اما درصد حدسی نمایش نمی‌دهد. مسیر خرید نیز پیام عمومی مناسب مشتری دارد.

آزمون اصلاح شامل callback واقعی هر دو دکمه، نمایش سطح و درصد در حساب حتی با flag خاموش، تخفیف دستی، سقف پلکان و زمان افت، خطاهای اتصال و اجرای واقعی `config:cache` با کلید ساختگی و بدون متغیر محیطی زمان اجرا است. بازگشت این اصلاح با برگرداندن کد دو مخزن و بازسازی کش تنظیمات انجام می‌شود؛ دادهٔ مالی یا تنظیمات سفارشی نیاز به پاک‌شدن ندارد.

## مرجع داده و دامنه

- مرجع تنظیمات: گزینهٔ موجود `ipsvp_loyalty_settings.customer` در وردپرس. تنظیمات نمایندگی تغییر نمی‌کند؛ نصب وصله تنظیمات ذخیره‌شده را بازنویسی نمی‌کند.
- مرجع تخفیف ثابت حساب متصل: ستون موجود `manual_discount_percent` سایت. صفر مستقل از NULL/خالی است.
- حساب هنوز متصل‌نشده: مقدار ثابت در گزینهٔ سایت `ipsvp_bot_customer_discount_{tel_id}` نگهداری می‌شود. هنگام اتصال یک بار به حساب سایت منتقل می‌شود؛ اگر سایت از قبل مقدار ثابت، حتی صفر، داشته باشد همان مقدار سایت مقدم است. پس از انتقال موفق، گزینهٔ موقت حذف می‌شود.
- مرجع پرداخت: هر تراکنش از محل اصلی ثبت آن خوانده می‌شود؛ هیچ دفتر مالی، تراکنش مالی، جدول موجودی یا شارژ جدیدی ساخته نمی‌شود.
- مبلغ‌ها تومان (`IRT`) هستند. تبدیل ×۱۰ یا ÷۱۰ انجام نمی‌شود.
- تخفیف حساب مانند سایت، یک بار **پس از** تخفیف محصول/تعرفه و قیمت‌گذاری موجود اعمال می‌شود. گردکردن نهایی مطابق سایت رو به بالا به تومان کامل است. خرید چندتایی، قیمت نهایی هر واحد را در تعداد ضرب می‌کند؛ مبلغ با قیمت واحدِ نمایش‌داده‌شده سازگار می‌ماند.
- خرید، تمدید و حجم اضافه فقط برای شناسه‌های سرویس اشتراکی که در تنظیمات محیطی صریحاً مجاز شده‌اند. برای نمایندهٔ ربات یا سرویس خارج از این فهرست، قیمت فعلی حفظ می‌شود.

| رویداد | محل اصلی محاسبه |
|---|---|
| رسید کارت‌به‌کارت ربات، نوع ۱/۲/۳/۴ و وضعیت ۱ | جدول موجود payments ربات |
| افزایش/کاهش اصلاحی مدیریت ربات | admin_credit / admin_debit موجود ربات |
| رسید و اصلاح مدیریت سایت | receipts موجود سایت |
| کپی شارژ سایت در ربات، دارای receipt_id یا منبع wordpress | از ربات حذف؛ اصل سایت محاسبه می‌شود |
| bot_wallet_mirror و bot_wallet_sync | از ادغام حذف می‌شوند |
| خرج کیف پول، انتقال، ارجاع، بازپرداخت، رمزارز، وضعیت غیرتأیید | پرداخت واجد شرایط جدید نیستند |

برای تطبیق شناسه، رویداد ربات کلید `bot:{payment_id}` دارد. رویداد تکراری حذف می‌شود؛ ردیف‌های ربات با روش و ref_id یکسان نیز یک بار صادر می‌شوند. پاسخ سایت به ربات و محاسبهٔ خود سایت از **همان محاسبه‌گر موجود سایت** استفاده می‌کنند. API خواندنی ربات هیچ درخواست بازگشتی به سایت ندارد؛ حلقهٔ HTTP تشکیل نمی‌شود.

پنجره معتبر `(اکنون - ۳۰ روز، اکنون]` است. رویدادها به ترتیب زمان تأیید پردازش می‌شوند. کسر اصلاحی فقط آخرین شارژهای معتبرِ قبل از اصلاح را مصرف می‌کند؛ به رسید مستقیم و شارژ بعدی سرایت نمی‌کند. خروجی ربات تا ۶۰ روز سابقه را می‌فرستد تا اصلاحات اخیر که ابتدا شارژ اکنون‌منقضی‌شده را مصرف کرده‌اند درست بازسازی شوند. تایم‌زون انتقال، epoch است؛ نمایش زمان افت سطح در ربات به وقت تهران است. برای زمان‌های برابر در دقت یک ثانیه، ترتیب منبع و سپس شناسه ثابت است.

## تغییرات ذخیره‌سازی

**مهاجرت ساختار دیتابیس لازم نیست.**

در JSON فعلی `payments.detail` این کلیدها اضافه می‌شوند:

- `loyalty_approved_at`: زمان اولین تأیید؛ تأیید دوباره یا ویرایش بعدی آن را تغییر نمی‌دهد.
- `customer_loyalty_quote`: مبلغ مبنا، مبلغ نهایی، درصد، منبع و زمان قیمت‌گذاری. `payments.price` و `pre_orders.data.price` از همین مبلغ نهایی استفاده می‌کنند. مسیر تحویل/پرداخت مجدد، قیمت جدید محاسبه نمی‌کند.
- در بازیابی اختیاری زمان‌های قدیمی: `loyalty_approval_evidence`، شناسهٔ مدرک ممیزی.

هیچ تغییری در مبلغ پرداخت‌های گذشته یا موجودی توسط قابلیت تخفیف انجام نمی‌شود. محافظ بازپخش تأیید API سایت داخل قفل تراکنش نیز بررسی می‌شود تا تأیید تکراری شارژ را دوباره اعمال نکند.

## داده‌های تاریخی — پیش‌نیاز دقت روز اول

ربات قبلاً ستون/فیلد زمان تأیید مستقل نداشت. `created_at` زمان ساخت پرداخت است و `updated_at` ممکن است بعداً تغییر کند؛ هیچ‌کدام به‌عنوان زمان تأیید فرض نشده‌اند. رسید قدیمی فاقد زمان تأیید قابل استناد، خودکار واجد شرایط نمی‌شود. در سایت هم برای مشتری عادی، `reviewed_at` لازم است و زمان ارسال جایگزین نمی‌شود.

فرمان جدید، بدون فایل، فقط تعداد زمان‌های نامشخص ربات را گزارش می‌کند:

```sh
php artisan loyalty:approval-times
```

برای بازیابی از لاگ معتبر یا خروجی تأییدشدهٔ ممیزی، CSV زیر تهیه شود؛ رویدادهای ۶۰ روز اخیر برای بازسازی اصلاحات اهمیت دارند:

```csv
payment_id,user_id,amount,approved_at,evidence
123,45,2000000,2026-09-20T12:00:00+03:30,approval-audit-123
```

پیش‌نمایش بدون نوشتن:

```sh
php artisan loyalty:approval-times reviewed-approvals.csv
```

**فقط پس از تأیید جداگانهٔ انتشار/بازیابی دادهٔ واقعی**:

```sh
php artisan loyalty:approval-times reviewed-approvals.csv --apply
```

کل فایل اعتبارسنجی می‌شود؛ شناسه، کاربر، مبلغ، وضعیت و روش پرداخت باید تطبیق داشته باشند. زمان موجود بازنویسی نمی‌شود. خطای هر ردیف کل عملیات را rollback می‌کند. تنها JSON مربوط به مدرک/زمان تأیید تغییر می‌کند؛ حتی `updated_at` هم عوض نمی‌شود. این فرمان روی دیتابیس واقعی اجرا نشده است.

## رابط مدیریت و کاربر

در مدیریت ربات: دکمهٔ مستقیم در منوی اصلی مدیریت و نیز تنظیمات ← «تخفیف پلکانی کاربران عادی». چهار خط `مبلغ:درصد` برای پایه و سه پله؛ پایه از صفر، مرزها صعودی، درصدها ۰ تا ۱۰۰ و غیرکاهشی. مثال پیش‌فرض:

```text
0:0
2000000:5
5000000:10
10000000:20
```

در جزئیات کاربر عادی: «تخفیف ثابت حساب». عدد صفر غیرفعال‌کردن تخفیف حساب است؛ دکمهٔ پاک‌کردن، حالت پلکانی را برمی‌گرداند. هر دو مسیر callback و پیام متنی دسترسی ادمین را بررسی می‌کنند. این تنظیمات در سایت ذخیره می‌شوند.

حساب کاربری: سطح حساب به تعداد ستاره‌ها، درصد خودکار حاصل از پرداخت‌ها، درصد و نوع تخفیف حساب، جمع معتبر ۳۰ روز، باقی‌ماندهٔ پله بعدی و زمان افت سطح فعلی در صورت وجود. زمان افت با فرض نبود رویداد مالی/تغییر تنظیمات جدید محاسبه می‌شود. دستی انقضا ندارد. نمایش اطلاعات حساب به فعال‌بودن قیمت‌گذاری وابسته نیست؛ اگر flag قیمت‌گذاری خاموش باشد، متن صریحاً فعال‌نبودن اعمال تخفیف در خرید ربات را نشان می‌دهد.

## اتصال‌ها

همه با کلید مشترک موجود `X-IPSABET-API-KEY`:

- ربات: `POST /api/wp-sync/customer-loyalty/events`، ورودی `tel_id`، فقط خواندن رویدادهای اصلی.
- سایت: `POST /wp-json/ipsvp/v1/sync/customer-loyalty/profile`، `tel_id` و در درخواست ربات snapshot رویدادها.
- سایت: `POST .../settings`، بدون customer خواندن؛ با customer نوشتن تنظیمات کاربران عادی.
- سایت: `POST .../override`، `tel_id` و `value`؛ رشتهٔ خالی پاک‌کردن، رشتهٔ `0` صفر صریح.

این API برای سرور مورد اعتماد دارای کلید است، نه مرورگر مشتری. ربات هیچ قیمت یا درصد ارسالی کاربر را برای تخفیف حساب نمی‌پذیرد. پاسخ ناموفق سایت، سفارش تخفیف‌دار جدید نمی‌سازد؛ پروفایل پیام عدم دسترسی نشان می‌دهد. پرداخت‌های از قبل قیمت‌گذاری‌شده از مبلغ ذخیره‌شده استفاده می‌کنند. فعال‌سازی اتصال، دسترس‌پذیری متقابل دو سرور را برای قیمت‌گذاری جدید ضروری می‌کند؛ در اختلال، از قیمت/تخفیف حدسی استفاده نمی‌شود.

## نتیجه آزمون‌ها

PHP 8.3.12؛ Laravel/PHPUnit از composer.lock موجود، بدون اجرای Composer scripts:

- ربات: **۴۱ آزمون، ۲۰۳ assertion موفق**؛ شامل آزمون‌های قبلی، هر سه مسیر واقعی ساخت پرداخت، نمایش مبلغ، بازپخش کیف پول، تأیید مجدد، احراز هویت، مدیریت و بازیابی زمان‌های قدیمی.
- سایت: `loyalty-test.php`: **۱۱۳ assertion موفق**.
- سایت: `loyalty-integration-test.php`: **۲۵۷ assertion موفق** (۲۰۰ assertion نمایندگی موجود در همین شمارش است؛ تغییر رفتار نمایندگی درخواست نشده).
- اتصال جدید: `customer-loyalty-sync-test.php`: **۵۳ assertion موفق**؛ مرزها، جمع، انقضا، اصلاح، منبع واحد، کپی‌ها، صفر/خالی، تنظیمات سفارشی، یکسانی سایت/ربات و انتقال مقدار ثابت هنگام اتصال.
- بررسی syntax تمام PHPهای جدید/تغییریافته موفق؛ route جدید ثبت شده است.

جمع: **۶۲۶ assertion**. آزمون احرازهویت‌شدهٔ شبکهٔ زنده، دیتابیس MySQL واقعی یا بار هم‌زمان چند worker اجرا نشده است. بازپخش ترتیبی و منطق قفل بررسی شده‌اند؛ تست استیج واقعی پیش از انتشار همچنان ضروری است.

تکرار آزمون در کپی مستقل:

```sh
composer install --no-scripts --no-interaction --prefer-dist
php vendor/bin/phpunit
# در کپی افزونهٔ سایت پس از اعمال وصله:
php tests/loyalty-test.php
php tests/loyalty-integration-test.php
php tests/customer-loyalty-sync-test.php
```

phpunit.xml دیتابیس `:memory:` را اجبار می‌کند و کلید رمزگذاری صرفاً آزمایشی دارد. برای آزمون از کپی بدون `.env` واقعی استفاده شود.

## ترتیب انتشار پیشنهادی — اجرا نشده

۱. قبل از هر انتشار، تأیید صریح مالک؛ ذخیرهٔ نسخهٔ کد فعلی، تنظیمات و backup دیتابیس‌ها. کد ربات برای بازبینی در همین مخزن است؛ وصلهٔ سایت در `patches/customer-loyalty/wordpress.patch` همراه manifest نسخهٔ مبنا قرار دارد. ابتدا در **کپی سایت** اجرا شود:

```sh
git apply --check /path/to/wordpress.patch
git apply /path/to/wordpress.patch
```

۲. در استیج، افزونهٔ سایت و ربات جدید را با flag غیرفعال نصب کنید. migration عمومی یا `composer setup` اجرا نشود؛ این قابلیت migration ساختاری ندارد.

۳. **شناسه‌های واقعی سرویس اشتراکی باید مشخص شوند.** جدول services در نسخه فعلی ستون نوع اشتراکی/اختصاصی ندارد. فعلاً فهرست خالی است تا به پروکسی، اختصاصی یا سرور تخفیف داده نشود. در ربات:

```dotenv
CUSTOMER_LOYALTY_ENABLED=false
CUSTOMER_LOYALTY_SHARED_SERVICE_IDS=شناسه‌های_تأییدشده_با_کاما
```

۴. کلید مشترک و URLهای فعلی را بدون تغییر دادن مرجع تنظیمات بررسی کنید؛ ساعت هر دو سرور هماهنگ باشد. API رویدادهای ربات باید قبل از فعال‌شدن اتصال سایت در دسترس باشد. زمان‌های تاریخی نامشخص ممیزی و در صورت وجود مدرک بازیابی شوند.

۵. در پیکربندی **استیج** سایت `define('IPSVP_CUSTOMER_LOYALTY_BOT', true);` و در ربات `CUSTOMER_LOYALTY_ENABLED=true` تنظیم شود. یک حساب متصل، یک حساب مستقل، درصد ثابت صفر/پاک‌شده، هر سه خرید و بازپخش شناسه آزمایش شوند. مبلغ قبل/بعد، موجودی و شمار پرداخت‌ها ثبت و مقایسه شوند. سپس با تأیید مالک همین ترتیب برای محیط عملیاتی انجام شود. هیچ secret نمونه‌ای جای secret فعلی قرار نگیرد.

## بازگشت امن

- برای توقف قیمت‌گذاری جدید: flag ربات false و ثابت سایت false. تنظیم cache محیط مطابق رویه فعلی استقرار همان سرویس و فقط با مجوز انجام شود؛ این راهنما restart خودکار ندارد.
- در صورت بازگشت کد، نسخهٔ قبلی هر دو سمت برگردد. فیلدهای JSON افزوده و قیمت‌های ثبت‌شده باقی بمانند؛ موجودی، رسید و پرداخت‌های پس از انتشار به backup قبلی برگردانده نشوند.
- تنظیمات مشترک فقط در صورت نیاز و با حفظ تغییرات ادمین به snapshot بازبینی‌شده برگردند. اجرای معکوس migration لازم نیست.
- برای اشتباه در backfill، فقط کلیدهای مربوط به ردیف‌های ممیزی‌شده با تطبیق evidence و snapshot پیش از تغییر بازگردانی شوند؛ حذف عمومی JSON یا دستکاری مبالغ ممنوع است.
