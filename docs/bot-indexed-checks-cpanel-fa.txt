سورس محلی آماده است. روی سرور نصب نشده و پیام آزمایشی برای مشتری واقعی ارسال نشده است.
بستهٔ bot-indexed-checks-final-2026-10-27.zip جایگزین بستهٔ اعلان قبلی است؛

تغییر مهم
جدول order_checks برای موعد هر سفارش ساخته می‌شود؛ خود جدول orders بازنویسی نمی‌شود.
چهار موعد جدا برای اعلان، وضعیت زمانی، دریافت مصرف پنل و نگهداری سفارش منقضی وجود دارد.
روی این موعدها ایندکس ساخته می‌شود. کرون فهرست موعدرسیده‌ها را با LIMIT می‌خواند،
سپس فقط همان شناسه‌ها را از orders می‌گیرد؛ JSON همهٔ سفارش‌ها هر دقیقه پیمایش نمی‌شود.
هر سفارش جداگانه ارزیابی می‌شود و وضعیت یک عضو دسته به بقیه اعمال نمی‌شود.
گذشت زمان به‌تنهایی برای رسیدن موعد اعلان کافی است؛ ویرایش شدن سفارش شرط نیست.

- پنل‌های قدیمی غیرپاسارگارد: حداکثر ۲۰ بررسی، با موعد جدا برای هر سفارش.
- دریافت مصرف و ارسال اعلان، هرکدام مهلت نرم ۴۰ ثانیه دارند؛ درخواست در حال اجرا ممکن است
  تا timeout خودش ادامه یابد. نگهداری و پنل قدیمی مهلت مشترک ۳۰ ثانیه دارند.
- قفل اجرا مانع اجرای هم‌زمان فرمان می‌شود. فشار واقعی سرور به سخت‌افزار و دیتابیس بستگی دارد.

راه‌اندازی اولیه و تغییر تنظیمات
سفارش‌های جدید و تغییرات عادی سفارش، همان موقع موعدشان ثبت می‌شود.
سفارش‌های قدیمی در دسته‌های ۲۰۰تایی وارد زمان‌بندی می‌شوند؛ این کار یک بار است، نه هر دقیقه از ابتدا.
برای نمونه، ۱۰هزار سفارش قدیمی دست‌کم حدود ۵۰ نوبت یک‌دقیقه‌ای برای ثبت اولیه لازم دارد.
کرون دیررس یا اجرای طولانی‌تر می‌تواند این زمان را بیشتر کند. سفارش‌های ثبت‌شده در این فاصله پردازش می‌شوند.
بعد از تغییر آستانه‌های ادمین، بازتنظیم موعد سفارش‌های موجود نیز حداکثر ۲۰۰تایی انجام می‌شود؛
پس تغییر تنظیمات برای همهٔ سفارش‌های یک مجموعهٔ بزرگ هم‌زمان اعمال نمی‌شود.
پاک کردن cache ممکن است این مرور اولیه را دوباره آغاز کند؛ ثبت پیام‌های ارسال‌شده در دیتابیس حفظ می‌شود.
از تغییر مستقیم اطلاعات سفارش با SQL خارج از مسیرهای برنامه خودداری کنید؛ ذخیره از سورس ربات/سایت
موعد را به‌روز می‌کند. افزودن خام سفارش جدید با شناسهٔ جدید در مرور اولیهٔ ادامه‌دار شناسایی می‌شود.

نصب در cPanel — پیش از فعال کردن کرون
۱. از سورس فعلی و دیتابیس سرور بکاپ بگیرید. بکاپ محلی مرحلهٔ قبل از این اصلاح:
patches/before-indexed-order-checks-2026-10-27.zip
این بکاپ سورس است و دیتابیس زنده یا .env سرور را شامل نمی‌شود.

۲. در File Manager پوشهٔ اصلی Laravel را پیدا کنید: همان پوشه‌ای که فایل artisan و پوشه‌های
app، routes، database و vendor را دارد. مسیر کامل آن را یادداشت کنید؛ پوشهٔ public مقصد نصب نیست.
ZIP را در همان پوشه بارگذاری و Extract کنید و فایل‌های app، routes و database/migrations را جایگزین کنید.
.env و دیتابیس را جایگزین نکنید. اگر کرون قبلی این برنامه فعال است، هنگام نصب موقتاً غیرفعالش کنید.

۳. در Advanced → Terminal، به پوشهٔ واقعی پروژه بروید و دستورات زیر را اجرا کنید.
نمونهٔ زیر فرض می‌کند مسیر /home/CPANEL_USER/bot و PHP نسخهٔ ۸.۳ است.
CPANEL_USER و مسیر bot را حتماً با مقدار واقعی جایگزین کنید. اگر پروژه از PHP ۸.۲ استفاده می‌کند،
ea-php83 را با ea-php82 عوض کنید. PHP خط فرمان باید با پروژه سازگار و حداقل ۸.۲ باشد.

cd /home/CPANEL_USER/bot
/usr/local/bin/ea-php83 -v
composer dump-autoload --no-dev --optimize
/usr/local/bin/ea-php83 artisan migrate --path=database/migrations/2026_10_27_000000_create_order_checks_table.php --force
/usr/local/bin/ea-php83 artisan optimize:clear
/usr/local/bin/ea-php83 artisan queue:restart

این migration فقط جدول جدید order_checks و ایندکس‌هایش را می‌سازد؛ دادهٔ سفارش‌ها را حذف یا
هم‌زمان منتقل نمی‌کند. اجرای موفق migration ضروری است؛ فقط آپلود ZIP کافی نیست.
فرمان کرون بدون این جدول با پیام مشخص متوقف می‌شود.
Composer باید با PHP سازگار اجرا شود؛ اگر مسیر/دستور Composer یا PHP در هاست متفاوت است،
از مسیر اعلام‌شدهٔ همان هاست استفاده کنید. وابستگی Composer جدیدی اضافه نشده است.
در هاست دارای OPcache بدون بررسی تغییر فایل، روش reload اعلام‌شدهٔ پشتیبانی هاست را انجام دهید.

اگر Terminal ندارید
از پشتیبانی هاست بخواهید دستورات همین بخش را در پوشهٔ پروژه اجرا کند. راه جایگزین برای migration:
پیش از کرون اصلی، یک کرون موقت یک‌دقیقه‌ای با Command زیر بسازید و پس از موفقیت آن را حذف کنید:
cd /home/CPANEL_USER/bot && /usr/local/bin/ea-php83 artisan migrate --path=database/migrations/2026_10_27_000000_create_order_checks_table.php --force >> /home/CPANEL_USER/bot/storage/logs/order-checks-install.log 2>&1
لاگ order-checks-install.log را در File Manager باز کنید و موفقیت نصب را بررسی کنید.
این جایگزین فقط مرحلهٔ migration است؛ پاک‌سازی کش و تازه‌سازی autoload را هم طبق بخش بالا انجام دهید.

تنظیم کرون اصلی در cPanel
۴. وارد Advanced → Cron Jobs شوید.
۵. در Add New Cron Job، Common Settings را روی Once Per Minute قرار دهید؛ یا دستی:
Minute: *
Hour: *
Day: *
Month: *
Weekday: *
۶. در کادر Command فقط دستور زیر را بگذارید؛ پنج ستاره را داخل Command ننویسید:

cd /home/CPANEL_USER/bot && /usr/local/bin/ea-php83 artisan schedule:run >> /home/CPANEL_USER/bot/storage/logs/scheduler.log 2>&1

مسیرها و نسخهٔ PHP مثال‌اند؛ آن‌ها را با مسیر واقعی پوشهٔ دارای artisan و PHP هاست جایگزین کنید.
اگر نام مسیر فاصله دارد، آن مسیر را داخل کوتیشن قرار دهید.
۷. Add New Cron Job را بزنید. اگر schedule:run برای همین پروژه از قبل وجود دارد، همان را ویرایش کنید؛
دو کرون جدا برای orders:sync-lifecycle و schedule:run لازم نیست.
اگر هاست هر دقیقه را اجازه نمی‌دهد، زمان‌بندی را با محدودیت هاست هماهنگ کنید؛ اعلان‌ها هم دیرتر بررسی می‌شوند.

بررسی پس از نصب
- در Terminal می‌توانید یک بار فرمان واقعی زیر را اجرا کنید:
/usr/local/bin/ea-php83 artisan orders:sync-lifecycle
این فرمان صرفاً تست نمایشی نیست؛ اعلان‌های واجد شرایط را ارسال و نگهداری سفارش را اجرا می‌کند.
- پس از یکی دو دقیقه، ادمین ← اعلان حجم و تمدید را باز کنید. زمان آخرین اجرا باید تازه باشد.
- در File Manager، storage/logs/scheduler.log و storage/logs/laravel.log را در صورت خطا بررسی کنید.
- CACHE_STORE باید پایدار باشد: file، database یا redis؛ array/null برای سرور مناسب نیست.
در حالت database جدول‌های cache و cache_locks باید موجود باشند؛ روی چند سرور، کش و قفل مشترک لازم است.
- باقیماندهٔ ۱ گیگ در اولین بررسی واجد شرایط تشخیص داده می‌شود؛ نمونه‌برداری دوره‌ای زمان لحظه‌ای را تضمین نمی‌کند.

بازگشت
کرون را موقتاً متوقف کنید، فایل‌های نسخهٔ قبل را برگردانید و autoload و cache را تازه کنید.
جدول order_checks می‌تواند باقی بماند و نسخهٔ قبلی از آن استفاده نمی‌کند؛ برای برگشت کد نیازی به
برگرداندن دیتابیس زنده یا حذف سفارش‌ها نیست. سپس کرون نسخهٔ قبلی را طبق راهنمای همان نسخه فعال کنید.

تأیید فنی
تست خودکار با SQLite و پاسخ‌های ساختگی تلگرام/پاسارگارد اجرا شده است؛ گزارش داخل TEST-RESULTS.txt است.
تست ۲۰هزار سفارش با دو اعلان موعدرسیده: فقط همان دو سفارش برای اعلان پردازش شدند؛ اجرای بعدی صفر بود.
EXPLAIN QUERY PLAN استفاده از ایندکس را برای هر چهار صف بررسی تأیید کرد.
تست فشار روی MySQL واقعی هاست cPanel و ارسال واقعی تلگرام انجام نشده است.
